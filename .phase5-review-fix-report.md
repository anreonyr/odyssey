## P1-E TOCTOU fix — final code shape

`src/kernel/space/mod.rs::install_derived` after the fix:

```rust
pub(crate) fn install_derived<R: Resource>(
    &self,
    parent: SlotId,
    new_cap: Capability<R>,
    new_name: String,
) -> Result<SlotId, CapabilityError> {
    // P1-E: take `parents.write()` FIRST as the serialisation
    // point. revoke_single / revoke_tree both take
    // parents.write() first; holding it here means any
    // concurrent revoke blocks until our insert commits.
    let mut parents = self.inner.parents.write().expect("cspace poisoned");

    // Parent-live precondition (against `slots`, not `parents`
    // — a parent is a slot in the cspace, so it lives in
    // `slots`; `parents` is the child→parent map and only
    // contains derived slots). Because we hold
    // `parents.write()`, the canonical lock order
    // (`parents → slots → names`) means no concurrent
    // revoker can interleave between the read below and the
    // write acquisition that follows.
    {
        let slots = self.inner.slots.read().expect("cspace poisoned");
        if !slots.contains_key(&parent) {
            return Err(CapabilityError::SlotEmpty(parent));
        }
    }

    let new_slot = self.allocate();
    let mut new_cap = new_cap;
    new_cap.bind_slot(new_slot);
    let cap: Arc<dyn AnyCapability> = Arc::new(new_cap);

    // Continue to hold `parents.write()` while we take the
    // remaining locks in canonical order. Lock-order
    // invariant is preserved across all callers.
    let mut slots = self.inner.slots.write().expect("cspace poisoned");
    let mut names = self.inner.names.write().expect("cspace poisoned");

    let prev = slots.insert(new_slot, SlotEntry { cap });
    if let Some(prev_entry) = prev {
        names.retain(|_, s| *s != new_slot);
        drop(prev_entry);
    }
    names.insert(new_name, new_slot);
    parents.insert(new_slot, parent);
    drop(slots);
    drop(names);
    drop(parents);

    Ok(new_slot)
}
```

The lock-order invariant `parents → slots → names` is now consistent
across install, install_derived, revoke_single, and revoke_tree (every
caller takes the parents write/read lock first). The D2 test
(`tests/concurrency/d2_install_derived_dead_parent.rs`) pins the
precondition directly via `install_derived_for_test`.

## Design trade-offs / blockers

1. **`#[cfg(test)]` does NOT propagate to the library crate from
   integration tests.** `pub(crate) fn install_derived_for_test` would
   not have been visible to `tests/concurrency/d2_install_derived_dead_parent.rs`.
   The chosen approach (`pub` + `#[doc(hidden)]`) is the standard
   Rust pattern for integration-test accessors. No back-compat re-export
   was added; the accessor is hidden from rustdoc so downstream
   consumers can't accidentally rely on it.

2. **Loom cannot permute production locks.** The production
   `CapabilitySpace` uses `std::sync::RwLock` and `std::sync::Arc`, which
   loom cannot intercept. The loom-driven exhaustive permutation in
   `loom_concurrent_grant_and_revoke_tree_yields_no_orphans` therefore
   uses a minimal loom-friendly model that captures the same lock-order
   invariant (`parents → slots`). The std::thread version is kept as a
   smoke test for the default build (gated by
   `#[cfg(not(feature = "loom-tests"))]`).

3. **`MockClock` does not advance during `std::thread::sleep`.** The
   `Capability::invoke` path measures elapsed via `start.elapsed()`
   where `start = clock.now()`. `MockClock::pinned` returns the same
   `Instant` on every `now()` call, but `Instant::elapsed()` compares
   against the real `Instant::now()`. So a pinned mock clock reports
   real elapsed time regardless of whether the handler slept. The
   M3 timeout test therefore uses the default `SystemClock` (factory
   `new(space)`); the MockClock path is exercised by
   `tests/delta/quota_clock_eviction.rs` for quota-window sliding,
   which does not depend on handler elapsed time.

4. **Interleaving 3 cannot be made to fire deterministically under
   std::thread** without controlling the scheduler. The deterministic
   version in `tests/concurrency/interleaving3_orphan.rs` reproduces
   the race shape by manually ordering operations: walk children →
   insert B → revoke_single(root) → revoke_single(A). This matches
   the production `revoke_tree` loop's per-frontier step exactly.

5. **No new architectural decisions** were required. Every fix was a
   small targeted change; no new types, no new modules, no Cargo.toml
   changes outside the optional `loom` dep that was already there.
